# Scratchtree landing page

Build with `pnpm build:site`. This copies the pinned `@barbajoe/css-lib` stylesheet and the existing synthetic editor overview into `website/dist`. The website has no browser JavaScript or analytics.

`release.json` owns the Mac and Arch download links, release notes, and observed Mac build environment. Update it when publishing an authorized app release, after verifying the included packages and their platform evidence. The build requires `downloadUrl` and `archDownloadUrl` to point to packages from the same release. The development screenshot is labeled separately from the downloadable release.

`mac-update.json` controls the Mac update offer independently of the download links. The site build publishes it at `/releases/mac.json`. Change it only after verifying that the signed archive and its detached signature are publicly downloadable. The initial feed is 0.3.2, so Scratchtree 0.3.2 will wait for a newer offer.

The favicon and header use unchanged 16px, 32px, and 32px-at-2x PNG representations from the approved native ICNS. The build reads those PNG payloads directly, preserving their size mapping and artwork. Link previews use the 512px representation from the same ICNS, declared as the Open Graph image. See the [branding record](../docs/branding/README.md).

Netlify publishes only `website/dist`. The account-check function and private server settings are outside that directory. Its private `SCRATCHTREE_ALLOWED_EMAILS` list is an eligibility check; Dexie still verifies OTPs and restricts account access. Adding a future account requires updating both that list and Dexie’s registered users. No Dexie management credentials are needed by this endpoint.

The live site is [scratchtree.netlify.app](https://scratchtree.netlify.app). Netlify publishes `website/dist` and the separate account-check function; publishing a desktop app requires an explicit release request. Once a release is authorized, its link updates, reviewed metadata PR merge, automatic deployment, and public download verification are required parts of the same task, as defined in the [release guide](../docs/RELEASING.md#website-links-and-automatic-deployment-required). Deploy from reviewed source, keep `.netlify` state and private environment files ignored, and verify the public page, asset hashes, native-origin preflight, and a synthetic unknown-account response. Do not read or transmit private allow-list entries for routine website verification; real-account acceptance requires its own applicable authorization. Do not send a real OTP merely to check eligibility.

The existing Netlify project is connected to `Barbacoa08/scratchtree` through the Netlify GitHub App, with `main` as the production branch. Merging changes into `main` triggers a hosted build and production deployment using the checked-in `netlify.toml`: `pnpm build:site`, `website/dist`, and `netlify/functions`. Publishing a desktop GitHub release does not update the landing page metadata automatically. After verifying the release assets, update `website/release.json` through a reviewed PR and merge it into `main`; a manual CLI upload is not needed for that normal path.

The allowed-email list stays in Netlify's server environment. Never prefix it as a public/Vite variable or inline it into the static site. The static builder does not read it. Public endpoint/database locations are not credentials; operator keys and real emails do not belong in Git. Update the desktop configuration, native CSP, and exact service origin whitelist together if those locations change.
